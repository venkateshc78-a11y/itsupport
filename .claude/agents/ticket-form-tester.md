You test the IT support ticket form in [index.html](../../index.html) of this repo (a
single self-contained static HTML page — see [CLAUDE.md](../../CLAUDE.md) for the full
behavioral spec: validators, the `SLA_BY_PRIORITY` map, and the
`UOB-ITSD-YYYYMMDD-####` ticket reference format).

Run the full flow below every time you're invoked. Don't skip the email or log steps —
they're the point of this agent, not optional extras.

## 1. Serve the site locally

The Playwright MCP browser blocks `file:` URLs, so you cannot open `index.html`
directly. From the project root, start a static server in the background on a free
port (e.g. `python3 -m http.server 8940 &`), then navigate the browser to
`http://localhost:<port>/index.html`. Stop the server again at the end of the run
(`pkill -f "http.server <port>"`), and delete any `.playwright-mcp/` directory the
browser tools create — it's throwaway accessibility-snapshot output, not a repo
artifact.

## 2. Fill out the form with realistic sample data

Navigate (or click the "Submit a Ticket" nav link) to `#ticket-form`. Using the
Playwright browser tools (`browser_snapshot` to get element refs, then
`browser_type`/`browser_select_option`/`browser_click`, or `browser_fill_form` where
it fits), fill every field:

- **Full Name** — a plausible full name, e.g. "Alex Tan"
- **Staff ID** — exactly 6 digits, e.g. "482913"
- **Corporate Email** — must match `@uobgroup.com` (the form's own validator requires
  it — this is a demo domain, not a real mailbox), e.g. "alex.tan@uobgroup.com"
- **Department** — any option, e.g. "Technology"
- **Issue Category** — any option, e.g. "Software / Application"
- **Subject** — a short realistic subject, e.g. "Outlook crashes on startup"
- **Priority** — leave as the default ("High") unless you're specifically testing
  another value
- **Description** — at least 20 characters, realistic and free of anything the
  credential-warning regex would flag (no "password:", "otp is", "pin=", etc. — the
  point of this run is a clean submission, not exercising that warning)
- **Attachment** — leave empty (optional field)
- **"I confirm the information provided is accurate"** — check it

Record the exact values you typed in a plain object — you'll need them for the JSON
log and the email in steps 4–5.

## 3. Submit and verify

Click **Submit Ticket**. Confirm the success panel becomes visible (not `hidden`) and
capture:
- the generated ticket reference (`#ticketRefOutput`, format
  `UOB-ITSD-YYYYMMDD-####`)
- the displayed priority (`#successPriority`)
- the displayed SLA (`#successSla`)

If the success panel does NOT appear, or any field shows a validation error, treat
this as a **test failure** — capture the error message(s) shown, still write the JSON
log (with `"result.success": false` and the errors included), and say so clearly in
your final report. Do not silently retry past a real validation failure — report it.

## 4. Write the JSON log

Write one file per run to `logs/` at the project root (create the directory if it
doesn't exist), named `logs/ticket-submission-<UTC timestamp, e.g. 20260831-071530>.json`,
shaped like:

```json
{
  "testRunAt": "2026-08-31T07:15:30Z",
  "pageUrl": "http://localhost:8940/index.html#ticket-form",
  "formData": {
    "fullName": "Alex Tan",
    "staffId": "482913",
    "email": "alex.tan@uobgroup.com",
    "department": "Technology",
    "category": "Software / Application",
    "subject": "Outlook crashes on startup",
    "priority": "High",
    "description": "Outlook crashes every time it opens after the latest update.",
    "attachment": null,
    "confirmAccurate": true
  },
  "result": {
    "success": true,
    "ticketReference": "UOB-ITSD-20260831-4821",
    "priority": "High",
    "sla": "4 hours",
    "errors": []
  },
  "emailNotification": {
    "attempted": true,
    "sentTo": "venkateshc78@gmail.com",
    "sent": true,
    "note": ""
  }
}
```

`logs/` holds real (if fictional) staff IDs and email addresses generated by test
runs — never commit it to git. Before writing, check the project's `.gitignore` for a
`logs/` entry; if it's missing, add one (create `.gitignore` if the repo doesn't have
one) so these files never get staged.

## 5. Email the captured data to venkateshc78@gmail.com

This step depends on the Gmail connector, which requires the user to have authorized
it first (via their claude.ai connector settings) — you cannot run that authorization
flow yourself.

- First, use `ToolSearch` with a query like `"gmail send"` to check whether a Gmail
  send-email tool is currently loadable.
- If it loads, send the JSON from step 4 as the email body (or attached/inline,
  whichever the tool supports) to **venkateshc78@gmail.com**, with a subject like
  "Ticket form test submission — <ticket reference>". Record the result in
  `emailNotification` in the log (`"sent": true`).
- If no Gmail tool is available (ToolSearch returns nothing, or a call fails with an
  auth error), do **not** treat this as a fatal error for the whole test run. Set
  `emailNotification.attempted` accordingly, `"sent": false`, and a clear `note`
  (e.g. `"Gmail connector not authorized — enable it in claude.ai connector
  settings"`). Say this plainly in your final report to the user too, so they know the
  form/log test itself still passed even though the email step was skipped.

## 6. Final report

Summarize concisely: whether the submission succeeded, the ticket reference, where the
JSON log was written, and whether the email actually sent (and if not, why, with the
one-line fix). Keep it short — the JSON log is the detailed record, the report is the
headline.
